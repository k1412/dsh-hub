# DSH Hub 性能与并发

[English](performance.md) | 中文

本参考将确定性的发布正确性与部署环境相关的性能分开。自动门禁不调用模型，也不把 Internet 时延计入结果；它证明路由隔离和控制操作响应能力，端到端延迟则由运维者在自己的 Hub 与节点上测量。

## 并发模型

每个已注册节点拥有独立的签名 WSS 连接、交付 Journal、连接代次和 Runtime 集合。Hub 按编码后的节点与 Runtime 所有权路由命令，不会让整个机群共用一个全局节点队列。

在一个 Runtime 内，Connector 提供两个交互槽和四个批量槽。回答待处理提问与审批、Goal 操作、会话变更和设置使用交互通道；历史、索引、目录发现和其他大体积读取使用批量通道。因此，占满批量工作不会消耗交互预留。Node Agent 也会先为命令结果和控制投影保留 Journal 容量，之后才抑制可重建的高流量 Stream Frame。

Fleet 读取会向符合条件的在线 Runtime 扇出请求，再合并官方快照。每个节点贡献有 2.5 秒预算；慢节点超过预算后使用最小索引的“暂不可用”行，不能拖住其他节点、接收其他节点的命令或替换其他节点的状态。

## 自动发布门禁

常规 `hub:test` 测试套件包含两个同时连接、签名身份／Journal／Runtime 均独立的节点，并要求：

- 并发聊天准确到达所属节点；
- 一个节点停滞时，另一个节点仍能完成控制工作；
- 一个节点断开后，另一个节点仍保持健康；
- 离线节点的命令绝不出现在其他节点的 Outbox；
- 重连只恢复断线节点自己的持久积压；
- 审计完成记录仍能准确归属节点与 Runtime。

Connector 测试会占满全部四个批量槽，再并发提交 Goal 与设置控制，并要求两项控制在释放任何批量槽前返回。浏览器发布验证还会检查生产 CSP、官方目录流程、桌面布局，以及 390 × 844 视口下的覆盖式侧栏、有界 Runtime 选择器、全屏设置页和零横向溢出。

浏览器门禁还记录桌面启动、手机启动、手机侧栏展开、设置页打开和设置 Runtime 原地切换五项耗时。2026-08-18 的正式验证构建分别为 336.26、319.27、82.95、104.85 和 80.76 ms；切换检查还要求设置页保持打开且 Document 身份不变。共享 CI Runner 对每项使用 2.5 秒的数量级回归预算并保存 JSON 制品。这些数字只覆盖本地静态资源与交互完成，不包含登录、节点往返或模型生成。

## 已知交互回归矩阵

正式发布把已经出现过的故障按产品行为固定在可执行门禁中：

| 行为 | 自动证据 |
|---|---|
| Fleet 同页汇总所有节点并按文件夹分组、附带节点标签 | 多 Runtime 聚合、ID 所有权与离线最小索引测试 |
| 新建会话可选节点并浏览该节点目录 | Hub Runtime picker 组件测试、官方目录 Bundle 与 CSP 浏览器测试 |
| 弹窗可关闭、创建可提交、会话可滚动且手机无横向溢出 | 固定官方 Web 快照、390 × 844 几何与交互耗时门禁 |
| 提问回答、Goal 暂停／清除不会变成 502 或永久 Pending | 签名双节点转发、交互 RPC 所有权、失败转 RPC Envelope 与超时监控测试 |
| 设置切换不整页刷新，也不发布旧节点晚到数据 | 390px 真实组合中的 Document 身份／设置可见性／耗时、URL 原地切换、全部 SettingsScope 刷新、插件清单重读与直接控制器代次测试 |
| 一个插件 Registry 404 不拖垮插件清单 | 混合 Registry／外部／单项不可用的 Node Agent 与 UI 测试 |
| 安装请求遇到 Cloudflare HTML 不显示 JSON 解析错误 | Bootstrap Content-Type、HTML 拦截诊断和敏感正文不回显测试 |
| 一个节点停滞、断线或恢复不影响另一个节点 | 同时在线双节点、交互预留、独立 Journal、断线恢复与慢 Fleet 预算测试 |
| 本地 Web、桌面端和 Hub 使用同一 Runtime | 真实 Cordis Loader 共存与共享 ApiProxy Session 测试 |
| 插件更新可自动恢复并保留显式回退，快照恢复受限于受管路径 | Supervisor 更新事务、制品版本、幂等快照、机密排除与乐观并发测试 |

执行确定性检查：

```bash
pnpm run hub:test
pnpm run hub:typecheck
pnpm run hub:lint
pnpm run build
pnpm run hub:web:csp:verify
pnpm run performance
```

## 可复现控制面基准

`pnpm run performance` 启动真实 Hub HTTP Server、WAL SQLite、八个 Runtime 的能力与最小索引，并让节点结果在下一事件循环通过 `command.result` 唤醒等待者。每个场景默认运行三轮，发布判定使用三轮 p95 的中位轮，同时把每轮 p95 写入 JSON；这样可保留共享 Runner 抖动证据，又不会让一次调度停顿直接伪装成持续回归。它不调用模型、不访问 Internet，也不经过真实签名 WSS，因此测量的是 **Hub HTTP、路由、SQLite、事件等待与 Fleet 合并开销**，不是手机到 NAS 的端到端延迟。

2026-08-18 在 Linux x64、Node 22.22.1 开发机上的一次干净运行：

| 场景 | 样本／并发 | p50 | p95 | p99 | 吞吐 |
|---|---:|---:|---:|---:|---:|
| 指定节点直接控制 | 200 / 16 × 3 | 16.20 ms | 19.67 ms | 48.36 ms | 924.15 次／秒 |
| 八节点 Fleet 读取 | 40 / 4 × 3 | 12.58 ms | 16.90 ms | 16.91 ms | 290.37 次／秒 |

测量期间完成 1,612 条命令，进程 RSS 从 150,331,392 增至 189,489,152 字节；直接控制三轮 p95 为 37.38、19.67、17.81 ms，Fleet 三轮为 17.26、16.90、16.83 ms。CI 即使失败也会保存完整 JSON 制品，并使用直接控制中位轮 p95 500 ms、Fleet 中位轮 p95 400 ms 的共享 Runner 回归预算；预算用于发现持续的数量级倒退，不是生产延迟承诺。可通过 `DSH_HUB_BENCHMARK_*` 环境变量改变节点数、样本数、奇数轮数和预算。

## 可观测指标

节点健康状态会公开等待结果的命令数、最旧 Pending 命令时长、最近 24 小时超时数，以及最近一次超时操作。浏览器直接控制等待超过 30 秒会收到 HTTP 504；Fleet 聚合对单节点使用 2.5 秒读取预算。两者都会产生一条不含 Payload 的超时审计，持久命令仍保持 Pending，可在稍后完成和对账。这些是故障收敛上限，不是性能目标。

交付 Journal 使用率达到 75% 时应告警，达到 95% 时应视为严重；排队的可重建 Stream Frame 达到 500 条或 4 MiB 时还会提前告警。会话历史等大型命令结果仍计入总字节数，但不会单独触发 Stream 抑制。增加限制前，应先调查重复超时、最旧 Pending 持续增长、频繁重连或 Journal 长期承压；这些信号通常意味着 Runtime 不健康、节点不可达、读取过大或节点资源不足。浏览器事件与应急终端 WebSocket 每 20 秒收到一次 Ping，因此在反向代理空闲超时点出现重连抖动属于部署故障，而不是预期轮询。

## 推荐部署 SLO

以下数值是节点在线且可达时的运维目标，不是本仓库宣称已经测得的成绩：

- 简单控制操作：节点在线且无压力时 p95 不超过 1 秒；
- Fleet 发现刷新：在运维者声明的基准机群规模下 p95 不超过 2.5 秒；
- 节点恢复：网络恢复可达后 p95 不超过 15 秒；
- 跨节点错误路由：严格为零；
- 受支持流程中的移动端横向溢出：严格为零。

记录任何延迟数值时，都应同时记录机群规模、节点到 Hub 的往返时延、历史大小、浏览器视口和观察窗口。模型生成时间是独立的负载指标，不能当作 Hub 控制面延迟。

## 预期瓶颈

Hub 按设计不提供透明的工作区、Transcript 或节点对象缓存。会话历史与文件数据保持节点权威，因此首次加载时延包含节点可达性、WSS 传输、本地 DSH 处理和 Payload 大小。大历史与索引会进入批量通道以保护交互，但仍会消耗节点 CPU、内存、带宽和浏览器渲染资源。

增加节点会增加 Fleet 发现的扇出工作。它不能削弱路由隔离；超过 2.5 秒预算的节点会暂时使用缓存行，而不会让最慢节点无限决定整页稳定时间。运维者应保持节点时钟同步，避免为 Journal 与 SQLite WAL 分配过小的 NAS 存储，并独立监控反向代理和 Cloudflare 超时，不要将其与 Hub 命令等待上限混为一谈。

## 真实双节点验收

发布部署后，让 NAS Runtime 与 `workstation-b` 同时在线，并完成：

1. 打开 Fleet 页面，确认两个节点的项目都按 Workspace 文件夹分组，并附带节点标签。
2. 先选择节点，再选择该节点返回的目录，分别在两个节点创建会话；无需切换 Fleet 过滤器即可同时发消息。
3. 从本地 DSH Web 或桌面端继续其中一个会话，确认 Hub 出现相同消息和 Goal 状态；再从 Hub 继续，确认本地客户端收到更新。
4. 在一个节点执行大历史或目录读取，确认另一节点的待处理提问、Goal 与设置控制仍可使用。
5. 断开一个 Node Agent，确认只有该节点不可用；排入一项符合条件的持久操作，重连后确认只恢复它自己的积压。
6. 在手机尺寸下检查创建弹窗、项目列表、会话滚动、问题回答、Goal 暂停／继续和设置目标切换。

如果出现响应路由到错误所有者、本地客户端无法共存、设置所有者含糊，或控制错误导致 UI 永久 Pending，就不能通过验收。
