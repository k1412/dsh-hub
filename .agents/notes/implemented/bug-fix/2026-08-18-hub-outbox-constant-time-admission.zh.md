# Agent Note: Hub 发件箱准入保持常数时间

Status: implemented

[English](2026-08-18-hub-outbox-constant-time-admission.md) | 中文

## 问题

可靠 Journal 在每次入队前都会统计全部保留记录并汇总所有正文字节数。填满支持的 10,000 条发件箱会因此执行逐渐增大的扫描，整体复杂度变成平方级。两个满容量回归与组装 Web 套件并行运行时，即使最终 Journal 数据完全正确，也可能超过共享 CI Runner 的超时。

字节总数不能只存在进程内存中。Hub 会在同一个控制数据库上反复打开 Journal，Node Agent 必须跨重启保留限额状态，崩溃恢复也必须看到与持久记录一致的值。

## 决策

Peer 状态在出站序列和确认游标旁持久保存 `outbound_bytes`。入队只读取这一行来检查记录数与字节数限额，并在同一个立即事务中插入正文、递增序列和字节总数。确认会一次性汇总被删除前缀的字节数，然后在一个事务中删除前缀并扣减其字节。记录使用量是两个持久游标之差，结果精确且无需扫描。

Schema 安装会检测在该字段出现前创建的数据库，增加带约束的计数器，并在正常构造 Journal 前根据保留的发件箱回填每个 Peer。迁移是幂等的，因此重新打开数据库不会重复统计或改变当前计数。

## 考虑过的替代方案

**增加测试超时。** 这会掩盖随负载变化的延迟，同时让离线节点积压较大时仍走平方级生产路径。

**在每个 Journal 对象中缓存使用量。** 不同 Journal 实例和进程重启会产生分歧，可能允许超过字节上限的准入，或在确认后错误拒绝工作。

**维护单独的汇总表。** Peer 状态已经拥有相关序列与确认游标，再增加一行及其生命周期只会增加同步工作，不能改善隔离。

## 结果

入队准入不再扫描保留正文，满容量测试可以在原有超时内轻松完成。字节限额在重新打开与升级后仍然有效。确认仍会对它即将删除的有界前缀执行一次汇总，但不会对每条排队记录重复执行。

迁移、确认、重新打开、配额、10,000 条分页、Node Agent 压力与多节点投递测试共同覆盖这些状态变化。
