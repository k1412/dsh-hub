# dsh-hub-transport

[English](README.md) | 中文

`@k1412/dsh-hub-transport` 提供 Hub 和 Node Agent WebSocket 循环下层的持久可靠投递状态机。重新连接会建立新的隔离连接代次，同时在 SQLite 中保留方向序列、消息标识、已接收的入站工作和未确认的出站正文。

## 投递合约

发送方在传输前持久化严格协议正文。每个方向分配单调递增序列，并附带接收方的累计确认。接收方验证签名 Envelope、节点、Boot、连接代次、有效期窗口和确认范围，随后在业务分发前持久接收下一个连续序列。

确认只删除已经确认的出站前缀。重新连接会为新连接代次和本地 Boot 重新签名相同的持久消息标识、序列和正文。发送游标会分页读取确认位置之后的全部记录，因此积压达到或超过单页上限时仍能继续排空。重复投递不会再次分发，序列缺口会要求权威重同步，旧连接会被代次隔离拒绝。

入站工作具有 `pending`、`processing` 和 `processed` 状态。分发前进程崩溃会留下 `pending` 工作；分发期间崩溃会留下 `processing` 工作，使能力层能够按已声明的只读、幂等、对账或禁止重试策略处理。传输重放不会假定部分执行的变更可以安全重试。

发件箱具有记录数和字节数限额，并公开记录数、字节数、最旧记录时间和配置容量供拥有它的进程实施背压与健康报告。序列游标与排队字节总数会和每次插入或确认在同一个 Peer 状态事务中更新，因此在队列接近 10,000 条上限时，准入检查仍保持常数时间。打开旧数据库时会先新增字节计数，并根据保留的发件箱回填，再接受新工作。已处理的入站正文会被删除，同时保留有界的去重元数据后缀。纯确认记录会合并，连接循环不会用另一条纯确认记录回应它。

## 模型体验

无。本包投递控制面记录，不注册任何面向模型的能力。

#### KV Cache 影响

无；可靠投递记录不会进入模型请求。

## 已知限制与后续工作

- 版本 1 接受 WebSocket 的连续顺序投递并拒绝缺口。可重建的高流量 Stream 从能力基线重新同步，不缓存任意乱序窗口。
- SQLite Journal 面向每个 Peer 数据库的单活动进程。多进程所有权需要外部租约，不属于本包范围。
